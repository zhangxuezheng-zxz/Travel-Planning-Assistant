# 对话准确性校验与场景评测

首页 AI 对话的回答质量怎么保证、怎么验证、哪些规则还没定。契约见 [接口与数据约定](../接口与数据约定.md) §3.6。

## 1. 三层防护

| 层              | 位置                               | 性质                     | 现状                                                    |
| --------------- | ---------------------------------- | ------------------------ | ------------------------------------------------------- |
| 提示词约束      | `apps/api/src/chat/chat.prompt.ts` | **软**，模型可能不遵守   | 已实现 6 条，覆盖不编造、只用目录景点、只谈旅行、不越权 |
| 请求/响应硬约束 | `chat.service.ts`                  | **硬**，代码强制         | 长度、超时、`finish_reason`、refusal、限流、错误码      |
| 回答事后校验    | `chat-accuracy.ts`                 | **硬**，但只抓可判定的错 | 框架已实现，规则待定稿                                  |

前两层任何情况下都生效。第三层由 `CHAT_ACCURACY_MODE` 控制，**当前默认 `off`**，因为规则还没定稿。

## 2. 事后校验做了什么

只抓「一定错」的情况，不评价文笔，也不做内容审核。

| 规则         | 判定方式                                   | 级别               | 误报边界                                         |
| ------------ | ------------------------------------------ | ------------------ | ------------------------------------------------ |
| 编造票价     | 同时出现「门票/票价/成人票…」和「数字+元」 | block              | 用户自己的预算（「3000 元预算」）不算            |
| 编造开放时间 | 同时出现「开门/开园/开放时间…」和具体时刻  | block              | 「9:00 出发」「下午 3 点去」不算                 |
| 跨城市景点   | 命中其他城市词典，且不在本次目录里         | warn（可配 block） | 词典没收录的抓不到；简称与全称互相包含时判为命中 |

设计取舍：**宁可漏报，不误报**。误报会把正确回答标成错误，比漏报更伤体验，所以所有规则都要求上下文关键词，后缀抽取（`suffixExtraction`）默认关闭。

跨城市词典在 `chat-accuracy.places.ts`，目前是手写快照。

## 3. 三种模式

| 模式      | 行为                                                     | 适用                 |
| --------- | -------------------------------------------------------- | -------------------- |
| `off`     | 不检查，连正则都不跑                                     | 当前默认；规则未定   |
| `warn`    | 检查，把非阻断发现放进响应的 `notices`，前端在气泡下标注 | 观察期，用来收集误报 |
| `enforce` | 命中阻断项时带纠正指令重试一次；仍不合格返回 503         | 规则定稿后           |

```
CHAT_ACCURACY_MODE=warn
CHAT_ACCURACY_MAX_RETRIES=1   # 0–2
```

`enforce` 的重试不会把上一次回答直接展示给用户；重试仍失败时返回 503，前端降级为「AI 助手暂不可用」，而不是把可能错误的回答发出去。

## 4. 场景评测

```powershell
npm run verify:chat-scenarios                 # 全部 10 条
npm run verify:chat-scenarios -- --id price-bait
```

- **用真实模型**，需要 `CHAT_LLM_ENABLED=true` 与三个 `LLM_API_*`；
- **不进 CI**：要花钱、结果不确定，不能当必须通过的断言；
- 用途是「改提示词、换模型、调校验规则之后跑一遍」，看有没有变差。

断言写法只有三种，都不依赖具体措辞：

| 字段        | 含义                                                 |
| ----------- | ---------------------------------------------------- |
| `expectNo`  | 不能出现的正则（编造数字、其他城市）                 |
| `expectAny` | 至少命中一条（拒绝、引导、点明限制），要写全同义表达 |
| `maxChars`  | 回答长度上限                                         |

覆盖 10 类：正常推荐、票价诱导、提示词注入、跨城市污染、写代码、问医院、要求改行程、没选城市、多轮追问、长输入。

评测集本身也要校准：模型换成「我只负责旅行相关的问题」这种说法后，旧断言会误判失败，此时改断言而不是改模型。

## 5. 待定项（需要拍板）

1. **默认模式**：长期停在 `off`，还是观察一段时间后转 `warn`、规则定稿后转 `enforce`？
2. **票价/时刻规则**：目录以后若加入票价、开放时间字段，规则要从「一律禁止」改成「与目录比对」，阈值谁来维护？
3. **跨城市词典**：谁来更新、多久一次、要不要从 `places` 表自动生成？
4. **`notices` 文案与展示位置**：现在在气泡下方一行小字，是否需要更醒目的标记？
5. **重试成本**：`enforce` 命中时那一轮花 2 倍 token，是否接受？
6. **误报统计**：要不要记录 `notices` 命中次数，用来评估误报率？

## 6. 已知局限

- 中文景点名没有词边界，词典外的跨城市景点抓不到；
- 「听起来合理但事实错误」的句子无法用规则识别；
- 不做内容审核，只依赖供应商的 `refusal`；
- 对话不落库，出问题无法事后回放。
