这是软件第二页“＋新建行程”打开的子页面。前端提供北京城市、日期、六类偏好、18个景点选择、规则推荐、每日安排编辑和服务器保存读取。浅灰底、白色圆角面板、横向步骤导航，青绿用于选中状态和主按钮。创建页样式作用于 `.trip-create-page`，列表与独立登录入口分别使用 `.trip-workspace`、`.trip-login`，未修改全局样式。

根目录执行 `docker compose up -d postgres`、`npm run db:migrate`、`npm run dev`，访问 http://127.0.0.1:5173/ 。App.tsx 现在提供可替换的注册/登录联调入口，使用已有真实鉴权接口；登录后进入行程列表，可新建或继续编辑。只运行 `dev:web` 无法完成服务器保存。

本机 3000 端口已有其他服务，因此忽略提交的 `.env` 中已将 `PORT` 改为 `3001`、`API_PROXY_TARGET` 改为 `http://127.0.0.1:3001`。团队成员使用各自空闲端口，两项配置需一致。没有停止其他项目服务。

已删除 JSON 导出、组件内部重复的退出提示页、无调用的旧缓存写入函数、隐藏装饰文字与死样式。旧缓存读取兼容继续保留。

## 页面接口

组件：`apps/web/src/features/trip-create/NewTripPage.tsx`。

| 参数                           | 用途                                                                     |
| ------------------------------ | ------------------------------------------------------------------------ |
| onBack（必传）                 | 父级处理返回第二页行程列表，组件内部不再创建重复退出页                   |
| onSaveDraft({title,draft})     | 保存服务器草稿；可返回 Promise，失败保留输入                             |
| onGenerateProposal(draft)      | 保存输入并请求服务端生成推荐方案                                         |
| onComplete(result)             | 确认服务端方案并保存人工编辑后的安排；本地安排不能直接当作服务端 planned |
| initialState                   | 加载完成后的初始草稿；切换资源时通过 key 重新挂载                        |
| initialView                    | 默认 wizard；已有本地行程可指定 trip                                     |
| storage                        | 替换本地缓存实现，正式登录后由父级按用户/草稿ID隔离                      |
| initialSchedule / initialTitle | 恢复服务器参考时间和草稿名称                                             |
| pageTitle / resetControl       | 编辑页标题，以及用户明确允许重排的状态                                   |

`onComplete` 的结果为 `{cityId, planningInput, trip}`，trip 保存每日 placeIds；与后端带 ScheduleItem 的正式 Trip 结构不同。未传服务端回调时只本地保存，页面不会假报服务器成功。

## 偏好与数据模型

偏好统一使用现有共享契约六类：历史文化/history、园林自然/nature、城市地标/landmark、艺术设计/art、亲子体验/family、老街与在地体验/local。保存与读取一一对应。长城作为景点分类保留，主题归历史文化；旧缓存中的长城主题按此规则迁移并去重。18个当前景点未覆盖所有主题，没有匹配景点的主题不会伪造推荐。

前端 `PlanningDraft` 为显示模型，包含 cityId/startDate/endDate/themes/pace/transport/selectedPlaceIds；适配器将中文主题转枚举、空日期转 null、transport 转 transportMode。服务端保存 ID 与 revision 由父级持有。

## 正式软件接入

```tsx
import TripWorkspace from './features/trip-create/TripWorkspace';

// 挂在软件第二页；user 和 getAccessToken 来自现有登录模块。
// getAccessToken 保持引用稳定，当前用户变化时通过 key 重建容器。
<TripWorkspace key={user.id} user={user} getAccessToken={getAccessToken} />;
```

可选 `api` 支持替换现有请求封装，默认同源 `/api`；可选 `onSignOut` 由宿主处理退出。若只接创建子页面，原有 NewTripPage 回调仍可单独使用，不强制采用这个列表或独立登录入口。

继续编辑时先 GET 读取最新 Trip，再通过 `fromServerTrip` 恢复草稿或已规划安排。只改名称或直接保存不会重算原时间；跨日期移动或排序会重算参考时间。增减已选景点、修改日期和偏好时，必须勾选允许重新规划，由适配器传 `acknowledgeScheduleReset`，然后重新生成、确认并保存人工安排。

缓存使用 sessionStorage，按用户 ID、行程 ID 和服务端版本隔离，仅恢复匹配版本；新建成功后移除匿名新建缓存，避免重复创建。缓存不是云端保存，页面明确要求点击保存。登录令牌仅在联调入口的当前标签页会话中保存，不存密码；正式软件可完全替换该入口。

保存/生成请求互斥，执行期间暂时禁用编辑；版本冲突不自动覆盖，部分失败保留最后成功资源 ID/revision。登录过期、冲突、方案过期和网络错误均提供对应提示。

## 二、行程草稿后端与对接说明（原 行程草稿后端交付.md）

## 已实现范围

所有路径前缀 /api，使用已有 Bearer token 鉴权。接口只从当前用户上下文取得 ownerId。

| 方法   | 路径                          | 输入/用途                                       |
| ------ | ----------------------------- | ----------------------------------------------- |
| POST   | /trips                        | { title, cityId }；创建 revision=1 的 draft     |
| GET    | /trips                        | page/pageSize，当前用户分页，默认 1/20，上限100 |
| GET    | /trips/:id                    | 读取当前用户的行程                              |
| PATCH  | /trips/:id                    | expectedRevision，title 和/或 planningInput     |
| PUT    | /trips/:id/selections         | expectedRevision、placeIds，保存景点选择顺序    |
| DELETE | /trips/:id?expectedRevision=N | 版本保护删除，204无响应体                       |

planningInput 支持 cityId、成对的 startDate/endDate、themes、pace、transportMode；不接受 selectedPlaceIds 或 days。空草稿可无日期、无景点；有日期时必须合法且包含首尾最多30天。中文主题与共享契约六类 Theme 枚举一一对应，保存读取不丢失主题。长城作为景点分类，兴趣归历史文化；旧浏览器缓存自动迁移。

读他人资源与不存在资源均返回404。未知字段/错误类型返回400。写操作在 PostgreSQL 事务中 SELECT FOR UPDATE 校验版本，并执行带 owner/id/revision 条件的更新；成功递增 revision，冲突返回409及 currentRevision。不在后台自动覆盖冲突。

已planned只改标题保留安排；改变规划条件或选择必须acknowledgeScheduleReset=true，否则409。确认后清空安排并转回draft。推荐确认、手动日程和版本保护删除均已实现；草稿保存本身不生成正式行程。

## 前端接口与调用顺序

新增 `features/trip-create/trip-draft-client.ts`：

- createTripDraftApi({ getAccessToken, baseUrl?, fetcher? })：create/get/list/update/setSelections。默认 /api，经已有 Vite 代理转发；token 来自 A 的登录模块，不在适配器硬编码或保存。
- toDraftPlanningInput：中文主题转枚举，空日期转 null。
- savePlanningDraft(api,draft,title,existingTrip?)：新建（如有需要）→更新规划输入→更新景点；每一步使用上一次返回的 revision。
- fromServerDraft(trip)：服务器草稿转为 NewTripPage 的 initialState；资源 ID 和 revision 由父级单独保留。只转换支持的北京草稿，拒绝 planned，避免丢失其每日安排。

多个 HTTP 请求不构成一个事务。`DraftSaveError.lastSavedTrip` 和 `.phase` 提供最后保存成功的资源、版本和失败步骤；父级必须保留该 ID，避免重试重复创建。冲突需要用户重新读取并处理，不自动重试覆盖。

NewTripPage 新增可选回调：

```ts
onSaveDraft?: (input: { title: string; draft: PlanningDraft }) => void | Promise<void>;
```

传入时显示“保存草稿”按钮；等待时防重复，失败保留输入。未接入时继续本地保存，页面不会声称服务器已保存。原 onBack/onComplete/initialState/initialView/storage 接口保持兼容。onComplete 仍是完整行程的未来提交入口，不能直接调用草稿接口伪造 planned。

A 的接入示意（以下变量由父页面提供）：

```tsx
const api = createTripDraftApi({ getAccessToken });
// remoteTripRef 保存服务端返回的完整 Trip，首次为 null。
async function handleSaveDraft({ title, draft }) {
  try {
    remoteTripRef.current = await savePlanningDraft(
      api,
      draft,
      title,
      remoteTripRef.current ?? undefined,
    );
  } catch (error) {
    if (error instanceof DraftSaveError && error.lastSavedTrip) {
      remoteTripRef.current = error.lastSavedTrip;
    }
    throw error;
  }
}
<NewTripPage onBack={returnToTripList} onSaveDraft={handleSaveDraft} />;
```

恢复：await api.get(id) → 父级保存 remoteTripRef → fromServerDraft 返回值传 initialState → 数据加载完成后挂载组件；切换资源时用 key 重新挂载。草稿缓存由父级按用户隔离。
